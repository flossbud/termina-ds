## What Phase 2 delivers

A read-only bridge carrying live game state from the C engine to the Compose UI
on the bottom screen. The publisher samples `gSaveContext`, `PlayState` and
`Player` once per frame on `SDLThread` and publishes 27 `int32` slots under a
seqlock; Compose polls at 10 Hz on the Android main thread and decodes them.

The visible deliverable is a deliberately undesigned debug readout, which Phase 3
deletes and replaces with a real HUD.

### Why item 8 is the one that matters

Items 1-7 exercise only `gSaveContext`, a static struct that is always
addressable, and pointers that stay valid for the whole of ordinary play. They
would pass identically on an architecture that is fundamentally unsafe.

The scene transition is the only moment `gPlayState` is set to NULL
(`mm/src/code/z_play.c:481`) while the UI thread is actively reading. Passing it
is what validates the central design decision: that every dereference happens on
the game thread inside the `OnGameStateUpdate` hook, and the UI thread only ever
touches integers that were copied while the pointers were live. Had the reads
been done from the main thread — the obvious, simpler design — this is where the
game would have hard-crashed.

## Representation notes surfaced during implementation

Values that look wrong on the readout but are faithful engine data, annotated in
the UI so they are not mistaken for decode errors:

- An unequipped C-button reads `255` (`ITEM_NONE` widened from `u8`), shown as
  `255(empty)`.
- `roomNum` can be `-1` while `PLAY_STATE_VALID` is set — the engine's
  `Room.num` is an `s8` where `-1` means invalid room. Shown as `-1(no-room)`.
- `playerYaw` is a signed binary angle in the engine's `s16` rotation units, not
  degrees. Shown raw and labelled `yaw(raw)`.

Also inherent, and documented in `GameSnapshot.h`: the save-derived slots
(health, magic, rupees, form, clock, buttons) are published unconditionally every
frame, including on the title screen and file select where no save is loaded.
There is no "save is loaded" flag; only `PLAY_STATE_VALID` hints at it.

## Defects found and fixed during implementation

Both were defects in the plan's own code, caught by review before reaching the
device.

**Unreachable "no frames yet" state.** The schema version was written only inside
`Publish()`, so any read arriving before the publisher's first frame returned an
all-zero payload carrying schema version 0 — which the Kotlin decoder rejects as
a mismatch *before* it checks the frame counter. First boot would have displayed
`SCHEMA MISMATCH native=0 expected=1`, the alarm reserved for a stale `.so` from
a bad re-glob, and the spec's documented `NO FRAMES YET` state would never have
appeared. Slot 0 is now seeded at static-initialisation time (`constinit`,
guarded by a `static_assert`). Fixed in `883a121d4`.

**Duplicated staleness classification.** `poll()` and `carryForward()` each
carried the same threshold comparison, so a future change had two sites and
nothing forcing them to agree. Extracted to a single `classify()`; the 1000 ms
boundary is now pinned by tests at exactly 999 ms and 1000 ms, which a `>` vs
`>=` regression would previously have passed. Fixed in `964e3340f`.

## Tooling trap worth remembering

`llvm-nm` is **not installed on the build host** — it ships inside the NDK in the
`termina-ds-build:latest` image. Run bare on the host with stderr suppressed, as
the plan originally wrote it, the command prints nothing: a false alarm
byte-identical to the real `GLOB_RECURSE` failure the check exists to catch. A
verification step whose failure mode mimics the bug it hunts is worse than none.

Equally: `./gradlew` prints `BUILD SUCCESSFUL` with `testReleaseUnitTest
UP-TO-DATE` while running no tests at all. Console text is not evidence; read the
counts from `Android/app/build/test-results/testReleaseUnitTest/*.xml`.

## Carried forward

- Item 9 (framerate measurement) has now been deferred through both Phase 1 and
  Phase 2. The bottom screen polls at 10 Hz and the publisher adds ~30 field
  reads per frame, so the expected cost is negligible — but it remains asserted
  rather than measured.
- Items 10 and 11 (background/return, TalkBack) not exercised this session.
  TalkBack matters more than usual here: accessibility is the stated reason the
  architecture chose Compose over ImGui, and it is still unproven on hardware.
  Every row of the readout carries a `contentDescription`.
